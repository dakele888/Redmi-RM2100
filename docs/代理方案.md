# 代理方案（ss-libev + DoH DNS 分流）

> 适用：Redmi RM2100 / 小米路由器 4A 千兆版，官方固件，无线 WAN（WISP）形态。
> 目标：在不换固件、不刷机的前提下，让局域网设备按「国内直连、其余走节点」访问网络。
> 本文只描述**机制与文件**；订阅链接、节点密码、WiFi 密码等不随包分发。

---

## 一、为什么是这套结构

这台机器 MIPS 1GHz / 124MB 内存，跑 xray 要吃 35MB，跑 ss-libev 只要 1.5MB。
所以默认内核选了 **ss-libev**，代价是它**不看域名、只看 IP**，DNS 解析质量变成决定因素。

实测过一个关键约束：**该机场拦截了 53 / 853 端口**（返回污染结果），只有 443 放行。
所以本地 DNS 不能直接 `ss-tunnel -L 8.8.8.8:53`，必须走 **DoH over 443**。

于是整条链路是：

```
LAN 客户端
   │ DNS 查询 (UDP 53)
   ▼
dnsmasq(53) ──┬─ 默认上游 114 / 223.5.5.5        （国内域名）
              └─ gfw 域名 → chinadns-ng(192.168.31.1:6537)
                                ├─ 不在 gfwlist → 114
                                └─ 在 gfwlist   → smartdns(127.0.0.1:6536)
                                                    → DoH https://8.8.8.8/dns-query
                                                    → 8.8.8.8:443（绑在 lo）
                                                    → ss-tunnel(443) → 节点
```

TCP 分流走另一条线：

```
PREROUTING -i br-lan -p tcp -j SS
  SS 链：管理面白名单 RETURN → chnroute RETURN（国内直连）→ REDIRECT :12346
                                                                  │
                                                        ss-redir → 节点
```

**关键技巧**：把 `8.8.8.8/32` 加到 `lo`，让 `ss-tunnel` 监听 `8.8.8.8:443`。
这样 smartdns 访问 `https://8.8.8.8/dns-query` 时，SNI / Host / 证书三者天然一致，
不需要 DNAT（本固件 DNAT 到本机地址不可靠）、不需要关证书校验。

## 二、文件

| 路径 | 作用 |
|---|---|
| `proxy/proxyctl` → `/data/route/www/cgi-bin/proxyctl` | 主控 CGI：面板接口、规则挂载、守护、内核切换 |
| `proxy/ss/ssctl` → `/data/route/ss/ssctl` | ss-redir / ss-tunnel 生命周期、节点探测、failover |
| `proxy/doh/dohctl` | DoH 链路：lo 地址 + 443 隧道 + smartdns + chinadns-ng |
| `proxy/proxy/sub_sync.sh` | 订阅同步：下载 → 解析 SS 节点 → 生成 config.json → 重启 |
| `proxy/proxy/rules_sync.sh` | 规则同步：chnroute → ipset、gfwlist → DNS 分片 |
| `proxy/patches/official_hook.sh` | 每分钟钩子：DNS 分片守卫、日志裁剪、设备流量计数 |
| `proxy/www/panel.html` | 自建面板（含「代理」页） |
| `proxy/proxy/config.tpl` | xray 配置模板（保留备用内核） |
| `proxy/doh/smartdns.conf` | smartdns：仅做 DoH 转发、限日志等级 |
| `proxy/dns_hijack.sh` | 可选的 DNS 接管（把 LAN 侧 53 全部拉回本机） |

**不随包分发**：`config.json`（含节点密码）、`sub.url`（订阅 token）、`nodes.list`、
`.ssnode`、`bin/` 下的二进制（`xray` / `smartdns` / `chinadns-ng` / `ss-redir` / `ss-tunnel`）。

二进制来源：

- `ss-libev`：仓库自带 `ss/usr/bin`（本包不含，随固件备份包 `router_mode_*.tgz` 里的老版本一起）
- `smartdns`：GitHub `pymumu/smartdns` release 的 `smartdns-mipsel`
- `chinadns-ng`：GitHub `zfl9/chinadns-ng` release 的
  `chinadns-ng@mipsel-linux-musl@mips32+soft_float@fast+lto`
- `xray`（备用内核）：`Xray-core` release 的 `Xray-linux-mipsle`

## 三、首次配置

1. **填订阅**：面板「代理 → 订阅与规则 → 节点订阅（Clash YAML）」填自己的订阅地址，点「保存节点并更新」。
   解析器只认 shadowsocks 节点；同订阅里的 vless / vmess 会被跳过（ss-libev 不支持）。
2. **选内核**：默认 `ss-libev`。要用 vless 需切 xray（面板「代理运行 → 内核」），内存从 1.5MB 涨到 35MB。
3. **选范围**：「全部设备」或「多台设备」（从设备列表勾选，按 IP 生成多条规则）。
4. **DNS 接管**（可选）：设备页「记录访问域名 · DNS 接管」勾上后，设备即使自设 114/223/腾讯 DNS
   也会被拉回本机解析。代价是依赖特定 DNS 的场景（企业 VPN 内网域名、自建 AdGuard）会失效。

## 四、自愈行为

| 场景 | 行为 |
|---|---|
| 当前节点不可用 | 5 分钟内探测到 → 8 秒复测 → 遍历其余节点切换（约 40 秒） |
| 全部节点不可用 | 连续 2 轮确认 → **刷新订阅**（直连下载）→ 用新清单再找一次 → 仍失败才撤规则退回直连 |
| ss-redir 崩溃 | `boot.sh`（cron 每分钟）拉起；起不来则撤规则，避免全屋打空端口 |
| DoH 链路失效 | `dohctl probe` 失败 → 重建 lo 地址 / 443 隧道 / smartdns / chinadns |
| DNS 分片丢失 | `official_hook.sh` 每分钟检查，少于 500 行即重建 |
| 硬故障撤规则后恢复 | 记住原范围，进程恢复且节点可用后自动重挂（10 分钟限频，防抖） |

## 五、已知边界

- **ss 内核下节点池只有 SS 节点**。订阅里 170+ 个 vless 要切 xray 才能用。
- **UDP 除 DNS 外不代理**（QUIC / 部分游戏语音会回落 TCP）。
- **机场拦 53/853** 是实测结论；换机场后可以改回 DoT（`chinadns-ng-tls -t tls://8.8.8.8`）更轻。
- **DNS 未缓存查询 0.6–1.5 秒**（302ms RTT × 多层握手，实测 TCP 重传率仅 0.08%，不是丢包），命中缓存 1 ms。
- 代理吞吐受节点限制（实测约 7 Mbps），本机 CPU 只用了 25% 单核，不是瓶颈。

## 六、DNS 性能调优与日志治理

### 6.1 缓存层

| 项 | 调整前 | 调整后 |
|---|---|---|
| dnsmasq `cachesize` | 150（内置默认） | **2000** |
| smartdns `rr-ttl-min` | 60 秒 | **600 秒** |
| smartdns `prefetch-domain` | 关 | **开**（TTL 到期前主动回源）|
| smartdns `serve-expired` | 关 | **开**（过期仍应答，后台异步刷新）|
| 国内上游 | 114 / 223.5.5.5 | 追加光猫 `192.168.1.1`（并发取最快）|

150 条缓存对一个普通网页（30–50 个域名）不够用，刷两个页面就淘汰一轮，这是冷查询频繁的主因。

`/etc/config/dhcp`：

```sh
uci set dhcp.@dnsmasq[0].cachesize='2000'
uci add_list dhcp.@dnsmasq[0].server='192.168.1.1'
uci commit dhcp && /etc/init.d/dnsmasq restart
```

`/data/route/doh/smartdns.conf` 追加：

```
prefetch-domain yes
serve-expired yes
serve-expired-ttl 86400
serve-expired-reply-ttl 30
```

> `min_cache_ttl` 在此版 OpenWrt 的 dnsmasq init 脚本中**不被识别**，写入 uci 不会生成对应运行时配置，已放弃。

### 6.2 域名预热

| 文件 | 作用 |
|---|---|
| `/data/route/dns-warm.txt` | 46 个常用墙外域名（Google/YouTube/GitHub/TikTok/Telegram/WhatsApp/Discord/OpenAI/Netflix 等）|
| `/data/route/dns_warm.lua` | 直接构造 DNS 包发 UDP 到 `127.0.0.1:53`，每批 8 个并发，`socket.select` 收包 |
| `/data/route/dns_warm.sh` | 3 行 wrapper，调用上面的 lua |
| cron | `*/10 * * * *` 每 10 分钟补一次 |

实测 46 个域名 **9 秒全部成功**，预热后入口域名解析 **1 ms**。

> 旧版用 busybox `nslookup` 做预热是伪成功的：它内置超时短于 DoH 的 1.3 秒，46 个域名"2 秒跑完"但实际全部超时未入缓存。

**固有边界**：内容 CDN 的动态子域无法穷举（`rr1---sn-*.googlevideo.com` 有数百个、TikTok 的 `api16-normal-c-useast1a` 随区域变化），只能覆盖 App 启动必经的入口域名。

### 6.3 实测对比

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 国内域名首次（冷） | 36–99 ms | 30–52 ms |
| 国内域名缓存命中 | 1 ms | 1 ms |
| 墙外域名首次（冷） | 842–1592 ms | 600–1500 ms |
| 墙外域名缓存命中 | 1 ms（有效期 60 秒） | 1 ms（有效期 600 秒）|

墙外冷查询的秒级延迟来自 **302ms RTT × 多层协议往返**：TCP 建连 1 RTT + TLS 1–2 RTT + HTTP/2 协商若干轮 + DNS 查询 1 RTT。

曾怀疑是 MTU 分片（`MTU 1492 + ss 加密头 62 > 1492`），已在 `OUTPUT` 链加 `TCPMSS --set-mss 1360` 并验证规则命中，
但 TLS 握手时间未改善。根因排查结果：**TCP 重传率仅 0.08%（612 万段 / 4834 次）**，链路干净，不是分片也不是丢包。

结论：**降低节点 RTT 是唯一有效手段**，路由器侧已无优化空间。

### 6.4 日志治理

`/tmp`（60MB 内存盘）：

| 文件 | 机制 |
|---|---|
| `/tmp/messages` | `tmpguard.sh` 每 5 分钟，>4MB 截到 1MB |
| `/tmp/*.log` | 同上，通配覆盖 |
| `/tmp/luci-sessions` | 超 200 个时清 1 天前 |
| `/tmp/*.XiaoQiang.invalid-user.log.*` | 按 pid 存活判断清理，避免删活跃句柄 |

`/data`（29.6MB flash）：

| 文件 | 机制 |
|---|---|
| `/data/route/*.log` | `logtrim.sh` 每天 4:30 裁到 200 行 + `official_hook.sh` 每分钟 `cap_file` |
| `/data/usr/log/messages` | `logguard.sh` >1MB 截到 256KB |

**`/data/usr/log/messages` 的来历**：官方 `/usr/sbin/log_collection.sh` 第 62 行 `cat $TMP_LOG_FILE_PATH >> $LOGREAD_FILE_PATH`，
把 `/tmp/messages` 全量追加到 flash，自身无轮转。开关是 `misc.log.redundancy_mode=1`。

实测 4.7 小时涨 1MB（约 5MB/天），而 `/data` 可用仅 13.4MB。原 `logguard.sh` 虽有该文件的硬闸，但阈值设在 **8MB**，
对可用 13.4MB 的分区来说来得太晚，已收紧到 1MB/256KB。

文件内容九成是 `PpeHitBindForceToCpuHandler, skb->dev to interface with 0 is unkown` ——
**无线 STA 拓扑下 PPE 硬件加速回退到 CPU 软件转发**的调试日志。它的增长速度可当作「硬件加速是否生效」的免费指标。

### 6.5 resolv.conf 持久化（踩过的坑）

`/etc/resolv.conf` 是软链接 → `/tmp/resolv.conf.auto`，由 netifd 生成。

**只 uci commit 不生效**，必须 `network reload`，否则 netifd 内存里仍是旧配置，DHCP 续约时会写回上游光猫的 DNS：

```sh
uci set network.wan.peerdns='0'
uci set network.wan.dns='127.0.0.1'
uci set network.wan_6.peerdns='0'
uci set network.wan_6.dns='::1'
uci commit network
/etc/init.d/network reload
```

> 手写 `/tmp/resolv.conf` 只能临时生效。曾因此误判「路由器 DNS 被污染」十几轮——
> 实际是 busybox `nslookup` **忽略服务器参数**、固定读 `/etc/resolv.conf`，而该文件已被覆盖回光猫地址。
> 验证 DNS 必须用 lua + `socket` 直接指定 host:port，或看 `tcpdump` 的真实转发目标。
